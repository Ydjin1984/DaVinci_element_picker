### Что уже устроено правильно (важно не сломать)

- `package.json` → `extensionKind: ["ui"]` (введено в 0.1.26): хост расширения — **локальная машина** (win32) даже при Remote SSH. Значит, Playwright запускает Chrome локально без всякого CDP и проброса портов.
- Сохранение пиков и клон-паков идёт через `vscode.workspace.fs` (`pickStore.ts`, `cloneStore.ts`) — при удалённом workspace файлы **автоматически пишутся на сервер**. Скриншоты снимаются с локального Chrome и байтами уходят в серверный workspace.
- То есть требование «браузер локальный, все данные на сервере» архитектурно уже реализовано. Проблема — в конкретных точках отказа под SSH.

### Наиболее вероятные причины сбоя (по убыванию вероятности)

1. **Расширение фактически исполняется на сервере**, а не локально. В UI есть бейдж версии: если при SSH-подключении он показывает `workspace · linux` вместо `v0.1.26 · ui · win32` — это оно. Так бывает, когда VSIX установлен в удалённый VS Code Server (или Cursor со своей реализацией Remote SSH размещает VSIX-расширения на сервере, игнорируя `extensionKind`). С серверного хоста локальный Chrome запустить невозможно в принципе — остаётся CDP, который сейчас требует ручного reverse-forward порта 9222, и без него всё падает с ошибкой.
2. **PowerShell-хелпер «Start Local Chrome (CDP)» запускает Edge вместо Chrome**: `localChromeDebugCommand()` проверяет chrome.exe только в двух путях (LOCALAPPDATA, Program Files), а третьим кандидатом сразу берёт **Edge** из Program Files (x86). Если Chrome установлен иначе — стартует Edge. Видимо, это и есть «Eagle» из сообщения пользователя (голосовой ввод: Edge).
3. **`obtainBrowser()` в auto-режиме**: признак «headless-сервер» — это `linux && !DISPLAY`. Если на сервере установлен `DISPLAY` (X11 forwarding, VNC, десктопный Linux), код пытается запустить браузер **на сервере** вместо CDP-first — окно либо невидимо, либо открывается серверный chromium/edge.

### Предлагаемый набор правок (v0.1.27)

- **A.** `localChromeDebugCommand`: массив кандидатов Chrome-first — LOCALAPPDATA → Program Files → Program Files (x86), и только потом Edge (PF86 → PF → LOCALAPPDATA). Плюс учитывать `elementPicker.browserPath` первым кандидатом, если это windows-путь.
- **B.** `obtainBrowser` auto-режим: для remote-linux хоста (`vscode.env.remoteName` задан, platform=linux, не WSL) — **CDP-first независимо от DISPLAY**; запуск браузера на сервере — только последний fallback.
- **C.** `unifiedBrowserError` + подсказки: точные шаги восстановления — «DaVinchi: Start Local Chrome (CDP)» на своём ПК, затем `ssh -R 9222:127.0.0.1:9222 <host>` (или `RemoteForward 9222 localhost:9222` в `~/.ssh/config`), затем Open browser.
- **D.** На activate при workspace-хосте — заметное предупреждение с шагами «установите VSIX в локальный VS Code/Cursor» (частично есть с 0.1.25, усилить).
- **E.** Релизный цикл: bump 0.1.27 + CHANGELOG + preflight + VSIX + установка в VS Code и Cursor (скилл `davinchi-release`).

Правки A–D не конфликтуют между собой и закрывают все три гипотезы; ничего из работающего локального сценария не затрагивают (там путь `launchLocalBrowser` → discovery, он остаётся прежним).

## 2026-08-11 — Kiborg: ревью причины и целевой архитектуры

### 1. Что пользователь хочет (acceptance)

| Слой | Где должно жить |
|------|-----------------|
| Окно Chrome (headful, dev-режим, пикер) | **Локальный ПК** (Windows/macOS) |
| Playwright / CDP-сессия | **Локальный extension host (UI)** |
| Скриншоты, HTML/CSS, clone pack, `.element-picks/` | **Remote workspace (SSH-сервер)** |
| Терминал агента / `@mentions` | **Remote workspace paths** (пути, которые видит сервер) |

Локально уже ок. Через Remote SSH «браузер не стартует» = extension host оказывается не там, или launch-стратегия ошибочно уходит в server-side / CDP-ритуал.

### 2. Корневая причина (VS Code / Cursor Remote model)

При Remote SSH всегда **два** host'а:

1. **UI host** — процесс редактора на ПК пользователя (`win32` / `darwin`).
2. **Workspace host** — Node на Linux-сервере (часто без `DISPLAY`).

Если `extensionKind` / фактическая установка = **workspace**, то:

- `chromium.launch()` ищет Chrome **на сервере**;
- нет GUI → fail (или headless Playwright-cache, бесполезен для пикера);
- пользователь видит: «не запускается браузер».

Это **не** баг Playwright «на SSH», а **где крутится extension host**.

История в репо подтверждает качели:

| Версия | Стратегия | Побочный эффект |
|--------|-----------|-----------------|
| 0.1.11–0.1.12 | CDP + reverse-forward 9222 | Работает, но хрупкий UX (Ports, скрипт) |
| 0.1.13 / 0.1.22 | `extensionKind: ["ui","workspace"]`, prefer UI + launch local Chrome | Правильный happy-path |
| 0.1.23–0.1.25 | жёстче CDP / remoteHeadless | регрессии: снова упор в CDP / server |
| **0.1.26** | `extensionKind: ["ui"]` only, launch local first | **целевое направление верное** |

Код сейчас (0.1.26) уже говорит: UI host → launch system Chrome → CDP fallback. Сохранение через `vscode.workspace.fs` → remote FS. Значит «не работает» у пользователя = одна из **оставшихся дыр** ниже, а не отсутствие идеи.

### 3. Диагностика «почему у меня до сих пор не стартует»

Проверить **badge** в панели/status bar (есть с 0.1.23):

| Badge | Диагноз |
|-------|---------|
| `v0.1.26 · ui · win32` (или darwin) + Remote workspace open | Host правильный. Ищем Chrome path / launch error. |
| `… · workspace · linux` | **VSIX крутится на сервере** — Open Browser почти всегда мёртв. |
| Старая версия / нет badge | Не тот билд / не Reload Window. |

Типичные fail-mode'ы при «правильном» `ui · win32`:

1. **Chrome не найден** на UI host → нужен `elementPicker.browserPath` = полный путь к `chrome.exe`.
2. **VSIX только на remote** — UI extension не активируется как ожидается; нужно **Install on Local** (не только SSH host).
3. **CDP fallback** без reverse-forward: `ECONNREFUSED 127.0.0.1:9222` — если launch упал, CDP не спасёт без порта.
4. **Poisoned `browserPath`** (Playwright cache / server path) — в 0.1.25+ чистится, но User settings могут остаться битыми до clear.

### 4. Баги / долг, которые я вижу в текущем коде (релевантно SSH)

**A. `Start Local Chrome (CDP)` через `createTerminal`**

`extension.ts` → `startLocalChromeProcess` создаёт terminal с `shellPath: "powershell.exe"`.  
При активном Remote SSH **default terminal = remote shell**. Даже UI-extension часто получает **remote** terminal → `powershell.exe` на Linux = fail.  
Правильный паттерн уже есть в `webviewRepair.ts`: `child_process.spawn("powershell.exe", …)` **на UI process**, без terminal API.

**B. `contextPath` / `imagePath` через `uri.fsPath`**

`pickStore` / `cloneStore` пишут через `workspace.fs` (ок для remote), но в attach-блок кладут `fsPath`.  
Для UI extension + remote URI `fsPath` может быть **не тем путём, который видит shell на сервере** (локальный-looking / другой mount).  
Агенту на SSH нужны либо **POSIX remote paths**, либо надёжные `@.element-picks/latest/...` (relative mentions уже частично есть — их надо сделать primary).

**C. UX при ошибке open**

В 0.1.26 short error only — хорошо против dump'а, плохо для «почему SSH». Нужен **один** actionable message: host kind + platform + «install VSIX locally» / «set browserPath» / optional CDP.

**D. Двойная установка**

`extensionKind: ["ui"]` не мешает старой **workspace**-копии жить на remote host и путать пользователя. Документ + activate warning (частично был в 0.1.25) должны остаться явными.

### 5. Целевое решение (договорённость, draft)

**Primary path (обязательный happy-path):**

```
Cursor/VS Code (UI host, local)
  └── DaVinchi extensionKind=ui
        ├── Playwright launch → local Chrome/Edge (headful)
        ├── inject picker / screenshot / CDP session local
        └── vscode.workspace.fs → .element-picks/* на SSH workspace
```

**Не требуется** reverse-forward 9222 для нормальной работы.  
CDP-команды = **advanced fallback** only (`browserMode=cdp` или launch failed + user wizard).

**Secondary path (fallback):**

1. Local Chrome `--remote-debugging-port=9222` через **spawn на UI host** (не remote terminal).
2. Reverse-forward Ports `9222`.
3. `connectOverCDP` (если extension вдруг workspace на linux — единственный realistic path).

**Инварианты (definition of done):**

1. Open Browser при Remote SSH открывает **видимое** Chrome-окно на ПК.
2. Select/Clone pick пишет файлы в **remote** `.element-picks/` (видно в Explorer remote workspace).
3. Badge = `ui · <local platform>` при Remote SSH.
4. Без ручного Ports/CDP в 95% случаев (Chrome установлен локально).
5. CDP helper не зависит от remote terminal.
